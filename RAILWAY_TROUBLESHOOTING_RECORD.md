# Railway Deployment Troubleshooting Record

This document records the two major critical issues encountered when deploying the MSG91 Dashboard to Railway, the root causes, and the fixes.

## Issue 1: 500 Error (The MAC is Invalid)

### The Symptom
Hitting the `/settings/tenant` page caused an instant 500 Server Error. The logs revealed a `DecryptException: The MAC is invalid`.

### The Root Cause
This occurs when the `APP_KEY` environment variable on the server does not match the `APP_KEY` used to encrypt data in the database. When the database was imported from the local environment to Railway, the encrypted strings in the `tenant_settings` table (specifically `msg91_auth_key`) were still encrypted using the local `.env` key. Railway was trying to decrypt them using its own autogenerated `APP_KEY`.

### The Fix
The `APP_KEY` in the Railway Variables dashboard must always exactly match the key that was used when the data was originally inserted. If test data is corrupted by a key rotation, you can clear the unreadable encrypted strings manually via Tinker:
```php
App\Models\TenantSetting::query()->update(['msg91_auth_key' => null, 'openai_api_key' => null]);
```

## Issue 2: 403 Unauthorized Action on Settings Pages

### The Symptom
Hitting any page protected by `RoleMiddleware` (like `/settings/tenant` or `/templates`) immediately returned a generic `403 Unauthorized action` for the owner account, even though the feature flags were correctly enabled.

### The Root Cause
The `users` table on Railway was entirely missing the `role` column. Because the column didn't exist, Laravel treated the user's role as `null`, which caused `RoleMiddleware` to block access.

**Why was the column missing?**
The migration that adds the `role` column (`2026_08_07_031738_add_team_management_fields`) was aborted by Laravel during deployment. It was aborted because the migration *before* it (`2026_08_06_081555_add_scheduled_at_and_cancel_to_campaigns`) crashed with a raw SQL syntax error: `syntax error at or near "check"`.

**Why did the previous migration crash?**
Laravel 11's Schema Builder has a known limitation with PostgreSQL. Calling `change()` on an `enum` column generates an invalid `ALTER COLUMN` syntax with an inline `CHECK` constraint, which Postgres strictly rejects.

### The Fix
1. **Migration Fix:** The campaign migration was updated to use raw `DB::statement()` calls specifically for PostgreSQL to safely drop and recreate the constraint, bypassing the schema builder bug.
2. **Data Fix:** Existing users created *before* the column was added had their roles explicitly forced to `'owner'` using Tinker to ensure `RoleMiddleware` recognizes them.
```php
App\Models\User::query()->update(['role' => 'owner']);
```
